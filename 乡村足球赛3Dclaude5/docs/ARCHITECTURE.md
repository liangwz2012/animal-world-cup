# 架构说明

## 一句话

比赛核心是纯 JavaScript 的确定性状态机，3D 只是它的一个渲染后端；
人物、动作、球衣、球场全部在运行时按参数生成，包里没有一张图。

## 分层

```
platform  →  app  →  ui / render  →  art
                 ↘  core（不认识 three，不认识 canvas）
                 ↘  content（不认识 three）
```

- `core` 只依赖数学与 PRNG。任何时候都能在 Node 里跑完整比赛，测试因此很便宜。
- `content` 只依赖 `core/prng`。它把「哪一个村」翻译成球队、球员和地域风格。
- `art` 依赖 three 与 `core/constants`，负责把参数变成几何体、贴图和姿态。
- `render` / `ui` 负责场景组织与交互，`app` 负责流程编排。

## 确定性

`createMatch({ seed })` + 同样的输入序列 ⇒ 逐帧一致的比赛。
实现要点：

1. 核心里禁止 `Math.random`，只用 `createPrng(seed)`；
2. 固定步长 30 Hz，渲染帧率不影响模拟；
3. 渲染层只读状态，不回写；插值只发生在渲染层。

这条性质是后续做回放、好友联机和「同一条链接开出同一支村队」的前提。

## 球与人

- 球永远是独立刚体，任何动作都只给它一次冲量，从不把它绑到脚上；
- 球员是一个带锁定时长的状态机（`PSTATE`），锁定期内玩家输入不能打断；
- 触球有冷却，带球是「把球推到身前」而不是吸附。

## 人物生成

```
身材原型（9 种） + 个体扰动 → measurementsOf() → 骨骼长度
                                   ↓
                        程序化放样 → 一体化蒙皮网格（约 1060 顶点 / 1400 面）
                                   ↓
              一张 256×256 图集（球衣/号码/脸/皮肤/袜子/球鞋）→ 1 个 drawcall
```

图集的躯干采用非线性环向展开：正面和背面各占 30% 的 U 空间，两侧各 20%，
于是背号能拿到约 76 像素宽。接缝放在正胸中线，并画成门襟，反而更像村队球衣。

**踩过的坑（两个都很隐蔽）**：

1. 放样三角形的绕序必须是 `(a,b,c)/(b,d,c)`，写反了会整体内翻——
   表现是「背号跑到胸前而且是镜像的」，因为看到的其实是模型内壁。
2. 头部贴图是圆柱展开：横向 96 px 对应整圈周长（约 5.28r），纵向 96 px 只对应头高
   （约 2.13r）。横向 1 px 的弧长是纵向的 2.5 倍，直接画圆的眼睛贴上去会被拉成裂缝。
   所有五官都要先按 `2.126/5.278` 的比例横向压扁再画。

## 动作

程序化曲线，没有任何动捕文件。

**关节方向约定（骨骼朝 -Y 生长、角色面向 +Z）**：

| 关节 | 正值 | 负值 |
| --- | --- | --- |
| `hip.x` | 大腿后摆（伸髋） | 抬腿向前（屈髋） |
| `knee.x` | 屈膝，脚跟往臀部收 | **反关节，禁止出现** |
| `ankle.x` | 绷脚背 | 勾脚尖 |
| `shoulder.x` | 手臂后摆 | 手臂前摆 |
| `elbow.x` | 反关节 | 屈肘 |

膝和肘的屈曲方向相反。早期版本把膝盖写成负值，小腿就从膝盖往前折，
看上去像"脚往前面踢"。现在有两条测试守着（任何动作膝盖不得为负、
射门时摆动脚必须甩到身体前方）。

另外两条硬规则：

1. **步频 = 速度 / 步幅**。步幅随速度从 1.28 m 增长到 2.0 m，
   循环位移与步幅的误差有自动化测试守着（< 6%），这是「脚不打滑」的保证。
2. **出脚必须三段**：蓄力（髋后摆 + 屈膝）→ 触球（爆发伸展）→ 随挥。
   测试会检查摆动腿的髋角先变负再变正。

动作层与移动层是加权混合的，进出各有 0.12 / 0.18 秒过渡，避免动作硬切。

**幅度也要守**：收腿用 `max(0,cos)^1.6` 把峰变窄，膝屈曲峰值控制在 60°(慢跑)~92°(冲刺)，
后蹬控制在 18°~38°。早期版本膝盖能屈到 137°、脚跟贴着臀部长时间停留，
观感就是"腿往后翘得像根辫子"。

## 卡通观感怎么来的

1. `MeshToonMaterial` + 一张 4×1 的三阶灰阶渐变贴图（NearestFilter），把光照切成色块；
2. 反向外壳描边：同一套 geometry / skeleton 再建一个 `SkinnedMesh`，材质
   `side: BackSide`，用 `onBeforeCompile` 在 `begin_vertex` 之后插
   `transformed += objectNormal * outlineWidth`——注入点在蒙皮之前，所以描边会跟着骨头动；
3. 比例：5.6 头身、短四肢、球形肩、手掌是压扁的球。

## 渲染预算

| 内容 | drawcall | 说明 |
| --- | --- | --- |
| 球员 | 每人 1 | 5v5 共 10，7v7 共 14 |
| 球场草皮 | 1 | 一张 1024 贴图含条纹、秃斑和全部白线 |
| 场景静物 | 2 | 地形/护栏/看台一批，地域小品一批（顶点色合批） |
| 观众 | 1 | 数百个朝向球场的四边形合并成一个几何体 |
| 球网 | 8 | 半透明，深度不写 |
| 横幅 | 2 | 主客队各一 |
| UI | 每个元素 1 | 摇杆和按键只改变换矩阵，不重传贴图 |

## 机位

- **横屏**（首发形态）：传统侧面转播位，看得见两个球门和整条推进路线；
- **竖屏**（备用，网页里改窗口比例就会切）：顺着球场长边、从进攻方向背后跟拍。

摇杆方向按当前机位换算（`world.screenToWorld`），所以两种机位下「往上推 = 往前跑」。

## 微信适配

`platform/wechat-adapter.js` 在 `import three` 之前求值，补齐
`window / document / navigator / performance`、主 canvas 的事件与样式属性。
只补 three 真正会摸到的那几个口子，不引入完整的 weapp-adapter。

发布闸门（`tools/verify.mjs`）会检查：主包 < 4 MiB、包内无图片音频、
产物不含 `eval` / `new Function` / `XMLHttpRequest` / `localStorage`、
垫片与真机验收标记存在、`game.json` 为横屏、源码不含敏感词、地名数据带许可声明。
