# 高清动态地名球衣设计

日期：2026-08-16  
状态：本地实现与自动门禁完成，待微信开发者工具/真机视觉验收

## 1. 目标

修复当前比赛中球衣像素偏低、阵容近景地名难以辨认、动态地名实际未稳定显示的问题，同时保持现有球员骨架、锚点、动作、场上逻辑尺寸、碰撞与操控手感不变，并确保微信小游戏主包不超过 4 MiB。

## 2. 已确认的真实基线

- 当前每张 `shirt_front.png` / `shirt_back.png` 只有 56×52 px。
- 8 套球队风格、主客/门将、正背面共 48 张球衣底图，合计约 151 KiB。
- 当前动态球衣在原始 56×52 Canvas 上直接绘制 4–6 个汉字，前胸基准字号 14 px，远景必然丢失可读性。
- 当前动态球衣测试使用模拟 Canvas，只证明生成、注册和字段替换合同成立，没有证明微信运行时画面中真的挂载成功。
- 改造前生成流程有 1.6 秒总超时；失败或超时后静默回退原球衣，因此会出现“代码和测试存在，但比赛里仍没有地名”的情况。
- 2026-08-16 改造完成后重新运行 `npm run verify`：主包约 3.09 MiB，普通资源分包约 8.94 MiB，主包与分包合计低于项目 20 MiB 门限。

## 3. 已选方案

采用“Image2 正式母版 + 胸衣 2×动态合成 + 短地名 + 多层身份识别”的方案。视觉预览证明 112×104 已能清晰呈现 2–4 字地名，因此没有继续升到 224×208，避免低端机额外内存和生成耗时。

### 3.1 静态球衣底图

- 正式球衣的款式、布料质感、领口、袖口、拼色和地域纹样必须由内置 Image2 生图产生；不得继续用本地 Canvas / SVG / 逐像素色块自行设计正式美术。
- 先由 Image2 生成无品牌、无赞助商、无固定文字和号码的正式球衣母版，再由工程脚本完成确定性的切片、透明蒙版、像素尺寸、压缩与骨架对齐。
- 程序仅允许做尺寸适配、色彩校准、透明边界、压缩和动态地名叠加，不得用程序花纹替代 Image2 的视觉设计。
- 球衣正背运行底图由 56×52 升为 112×104（2×）；袖子、短裤、球袜和球鞋保持原骨架物理像素，只覆盖现有 8 套球衣风格，不按行政区复制素材。
- `team.json` 中球衣附件的逻辑尺寸继续保持 56×52，骨架锚点、位置和旋转不变；高分辨率图片只增加纹理采样密度。
- 项目保留 8 张最长边 512 px、透明 WebP 的 Image2 可编辑参考母版，合计约 421 KiB；正式运行图导出为调色板 RGBA PNG。
- 高清球衣改造后资源分包约 8.94 MiB，相对改造前约 9.04 MiB 反而减少约 0.10 MiB；全部进入 `runtime-assets` 普通资源分包，不进入主包。

### 3.2 动态地名合成

- 用户选定双方地区后，在赛前阶段把 112×104 底图绘入同尺寸离屏 Canvas。
- 地名在 112×104 上以系统中文字体绘制，不携带中文字库文件。
- 合成结果保留 112×104 纹理，运行时附件逻辑尺寸仍是 56×52。
- 每场只保留当前主客队的 12 张动态纹理；切换比赛时删除上一场注册项，并把渲染缓存限制为 12 张。
- 12 张 RGBA 纹理原始像素内存约 0.53 MiB，不含运行库自身纹理对象开销。

### 3.3 名称显示规则

- 球衣胸前只显示当前选择层级的最末级短名，目标长度 2–3 个汉字，例如“镇隆”“水口”“信宜”。
- 不把“广东广州”“信宜镇隆”等多级名称拼在球衣上。
- 自定义队名保留完整名称用于阵容、比分牌、场边牌和分享卡；球衣短名通过安全规则去除“足球队 / 球队 / 青年队 / 村 / 镇”等通用后缀后取 2–3 个字符。
- 任何自定义名称先通过既有微信内容安全流程；未通过时不得生成球衣纹理。
- 球衣文字是身份细节，不承担全场远景的唯一识别责任。全场远景继续由队色、比分牌和双方场边牌共同保证识别。

## 4. 运行链路

1. 用户完成主队地区选择，客队自动匹配或手动选择。
2. 选择页立即解析双方完整名称与球衣短名。
3. 后台预热主客队 12 张动态纹理，不等点击“立即开赛”才开始。
4. 逐张记录“底图加载、Canvas 绘制、导出、运行时注册、球队附件注入”状态。
5. 点击开赛时检查 12/12 是否完成；未完成时只做一次短重试。
6. 成功后启动比赛并在真实球队集合上检查 `injected=12`。
7. 失败时保留基础球衣，但阵容、比分牌、场边牌仍显示完整队名；同时写入可读诊断信息，不能再静默声称成功。

## 5. 阵容与比赛显示

- 阵容近景卡片使用高清动态球衣缩略图，球衣短名在常规手机横屏下可辨认。
- 阵容卡片同时显示完整队名文本，字号不小于既有主要球员名标签。
- 比赛近景、庆祝和回放中可读球衣短名；全场镜头不强求读清胸前小字，但队伍身份必须通过比分牌和场边牌持续可见。
- 正面短名避开衣领与手臂遮挡；背面短名的中心线位于球衣高度约 29%，避免贴近领口或超出背部，并避开下方号码图层。
- 原引擎继续为每名球员动态生成 1–99 号数字号码，号码附件保持原骨架锚点和旋转，位于背部中下段；使用浅色数字与深色细描边提高小尺寸可读性。

## 6. 包体与性能门禁

### 6.1 主包

- 不新增全国行政区图片，不新增字体文件，不把运行时生成图片写入上传目录。
- 本次新增主包内容仅限绘制、缓存、状态检查和 UI 接线代码。
- 内部目标仍为主包 ≤3.4 MiB；硬门保持 ≤4 MiB。
- 若实现后主包超过 3.4 MiB，必须先优化或移动非首屏内容，不进入交付。

### 6.2 分包与总包

- 高清基础球衣只进入 `runtime-assets` 普通分包。
- 48 张基础球衣新增预算 ≤700 KiB。
- 主包与普通分包合计继续保持 ≤20 MiB 项目硬门。

### 6.3 运行内存

- 当前比赛最多保留 12 张 112×104 动态纹理。
- 切换球队或退出比赛时释放旧纹理、Data URI / 临时文件映射和 Pixi BaseTexture。
- 不允许按全国行政区建立持久图片缓存。

## 7. 命名清理

- 将动态图片注册表和运行钩子中残留的 `__ANIMAL_*` 内部变量改为 `__RURAL_FOOTBALL_*`。
- 构建注入、平台适配器和测试同步修改，避免旧品牌标识继续进入发布代码。

## 8. 验收标准

### 8.1 自动验证

- 48 张球衣正背基础图均为 RGBA，像素尺寸 112×104；小部件保持原像素，透明边界与原附件锚点约束一致。
- 动态合成输出为 112×104；球队附件逻辑 `width=56`、`height=52` 不变。
- 主客队、3 类球衣、正背面共 12 张均注册并注入。
- 超时、导出失败、注册失败、附件缺失均有独立测试和明确状态。
- 缓存切换测试证明上一场动态纹理已释放。
- `npm run check` 全部通过。
- `npm run verify` 报告主包 ≤3.4 MiB、总包 ≤20 MiB。

### 8.2 视觉验证

- 球衣必须达到正式足球队服观感，具有可信的运动面料、领口、袖口和专业拼色；不得保留当前简单色块和机械横条感。
- 球衣风格与现有人物的中国本土化半写实 3D 卡通风格统一，不使用欧美俱乐部标识、知名品牌三条纹或现成赛事徽章。
- 阵容画面中“镇隆”“水口”等 2–3 字地名清晰可辨。
- 正面、背面、镜像方向、主客颜色、门将球衣均正确。
- 球员五种体型、走跑、带球、射门、倒地、庆祝时不出现球衣放大、偏移、露缝或锚点漂移。
- 正背面球衣继续绑定同一 `chest_shirt` 插槽；走、跑、冲刺、射门、铲球、前扑倒地和滑跪庆祝的正背动作必须同时存在。
- 比赛画面截图中队伍完整名称始终可通过比分牌或场边牌辨认。

### 8.3 微信环境验证

- 开发者工具完成一次冷启动和第二次缓存启动。
- 用户负责的真机验收至少覆盖一台 iOS 与一台 Android；本地自动测试不能冒充真机结果。

## 9. 非范围

- 不为全国省、市、县、乡、村预生成球衣图片。
- 不改变球员物理碰撞、速度、能力值和操控逻辑。
- 不在本次改造中重做人物骨架或动作。
- 不把全场远景胸前小字作为唯一身份提示。

## 10. 风险与降级

- 高分辨率纹理是否严格按 56×52 逻辑附件显示，必须通过真实 Pixi/Spine 运行画面验证；若发现纹理物理放大，改为在纹理加载后显式设置 `orig/frame` 与附件逻辑尺寸，不能直接缩回低清图片。
- 个别微信基础库的 OffscreenCanvas 导出能力可能不同，因此实现需保留 Data URL、Blob 和临时文件三条导出路径，并记录实际命中路径。
- 已采用 2×动态纹理作为清晰度、包体、生成耗时和低端机内存之间的最终平衡，不回退到 56×52 直接写字。
