# 《人人躲猫猫》多版本失败复盘

> 审计日期：2026-08-02
> 审计对象：`/Users/mac/Downloads/同步空间/AI/GitHub同步-liangwenzheng/人人躲猫猫`
> 用途：约束《乡村足球赛》3D 升级，不修改被审计项目

## 1. 一句话结论

《人人躲猫猫》不是败在某一个大模型或某一个引擎，而是败在**没有让微信真机、最终资产品质和完整对局成为不可绕过的停止门**。AI 很快地完成了大量局部功能和截图，也同样很快地放大了方向切换、原型堆积、版本漂移和“程序化方块冒充最终美术”的问题。

《乡村足球赛》必须吸取的核心经验是：**模型负责提速，证据负责决策；引擎只是运行容器，最终画质由资产主管线和视觉验收决定。**

### 2.1 大模型证据的可信边界

仓库共有 58 个提交，其中提交尾注统计为：

- 24 个提交自报 `Claude Fable 5`；
- 17 个提交自报 `Claude Opus 4.8 (1M context)`；
- 17 个提交没有对应模型尾注。

这些尾注能说明开发会话曾这样记录，但 Git 尾注是可编辑文本，不能独立证明服务端实际调用的模型。没有证据支持把 Unity、hidecat-v2、WorkBuddy 阶段强行归给某个具体模型。

同样需要区分两类 AI：

- 上述 Claude 名称主要代表**写代码和改工程的语言模型**；
- 仓库文档提到 Meshy、混元 3D、Rodin 等资产模型，但明确写着“未实测、缺 Key”或仅作建议，不能说这些模型真正产出了正式美术。

## 3. 失败证据

### 3.1 写了门禁，但没有执行门禁

2026-07-11 的正式设计写明：Unity 空 URP 场景必须先经微信转换，在至少一台 iOS 和一台 Android 真机通过；未通过前不得继续堆功能。实际仓库随后完成了 Unity 路线、整校 FBX、角色、材质和 44.2 MiB WebGL 构建，却没有找到微信转换产物和双端真机报告。

这说明“文档里有验收标准”不等于项目真的被验收标准约束。

### 3.2 产品范围在旗舰场景没过审前爆炸

原始范围是广外南校区约 100 米纵向切片，明确“不制作完整校园、不同步生产其他大学”。数天内实际扩成：

- 南北校区完整小星球；
- 93 所大学地图与 6 个分包；
- 100 所中小学数据清单；
- 城市、景点、名画古董四个模式；
- 巴黎、东京、伦敦等全球地标试验；
- 网页、微信、Unity、扫描重建多条发布线。

旗舰场景尚未达到用户预期，就先扩大内容数量，导致“每个地方都有，但每个地方都不够好”。

### 3.3 视觉问题被错误地当成渲染器问题

实际截图显示：

- 微信版近景是大面积红色挤出楼块、简化树木和通用 GLB 人物；
- hidecat-v2 虽加入砖纹、窗格、晚霞和后期，主体仍是重复楼层与程序化构件；
- Unity 工作记录自己承认，核心瓶颈是程序化占位 FBX、两张地面贴图和纯色材质，而不是后处理开关；
- 部分所谓“高品质”截图实际是带 Google Maps 署名的实景 3D 瓦片，既不代表自有资产，也不能直接打包成产品。

换引擎可以改变工具和渲染能力，但不能自动补出干净拓扑、可信比例、服装细节、统一骨架、表演动画、PBR 材质和地域文化考证。

### 3.4 验收物与交付目标错位

项目有大量 Playwright 截图和自检脚本，但主要证明“某个页面在桌面浏览器某一帧能显示”。它们没有覆盖：

- 微信双端真机；
- 10 分钟热机帧率与 1% low；
- GPU/纹理内存；
- 前后台恢复和弱网；
- 本地/远程分包校验；
- 完整一局的输入手感；
- 熟悉场景用户的盲测识别率。

更严重的是，`unity-client/Previews/preview-aerial.png` 与 `preview-library.png` 是完全相同的全黑图，仍保留在“Previews”中。截图数量没有转化为可靠的质量门。

### 3.5 引擎与版本基线持续漂移

同一批文档分别指定 Unity 2022.3 LTS、Unity 6.3 LTS，实际工程则是 Unity 6000.5.3f1。微信小游戏路径使用 Three r133 兼容包，网页路径同时升级到 Three 0.185，造成材质、色彩空间、Shader、动画和 API 的大量兼容垫片。

版本没有冻结，AI 容易把不同年代 API 混合，修复一个兼容问题又引出另一个。

### 3.6 重构和并行先于稳定的视觉样板

`hidecat-v2` 在视觉英雄资产未过审前就拆成七个并行模块，再统一集成。并行提高了代码产量，却没有解决同一角色、同一建筑和同一镜头究竟要达到什么最终品质。

仓库现状能看到这种结果：

- 约 50 个 HTML 入口；
- 34 个顶层截图/探针脚本；
- `src/hidecat` 约 15,148 行 TypeScript；
- `hidecat-v2` 又有约 8,044 行 TypeScript；
- 49 个已修改文件和 296 个未跟踪项；
- `scene-pipeline` 约 3.5 GiB，Unity 工程约 2.6 GiB。

大量实验没有被淘汰、归档或转化成唯一生产路径，维护成本持续升高。

### 3.7 自动测试偏规则，缺少产品级端到端门

服务端有 5 个规则/房间测试，场景管线有 4 个 Python 测试，这是值得保留的基础。但主网页和 hidecat-v2 没有 `test` 脚本，Unity 工程虽引用 Test Framework，却没有对应的游戏验收测试目录。视觉截图也没有阈值比较、黑帧检测和真机性能报告。

因此项目能证明若干算法局部正确，却不能证明产品整体达标。

## 4. 值得保留的成功经验

失败项目并非没有可复用成果，以下做法应进入《乡村足球赛》：

1. **纯 TypeScript 规则和服务端权威思想**：玩法不应绑定渲染器。
2. **资源失败回退**：角色、场景和网络失败均需要本地可玩兜底。
3. **固定步长、碰撞数值测试、地图清单校验**：这些比单帧截图更可信。
4. **真实资料与可分发资产隔离**：参考图、地图数据、许可证登记不能混入运行包。
5. **共享骨架和动画复用**：能显著降低角色包体和动画维护成本。
6. **地图分包经验**：93 校数据按需加载验证了“数据可分包”，但新项目只在内容质量通过后扩量。
7. **固定机位截图**：继续保留，但增加金图差异、黑帧检测和真机截图来源标记。

## 5. 对《乡村足球赛》的强制改进

| 旧项目问题 | 新项目规则 |
| --- | --- |
| 先宣布引擎，再证明选择 | LayaAir/Galacean 用同一微型切片竞测；硬门不通过即淘汰 |
| 网页截图代替微信验收 | 每个运行里程碑必须有开发者工具、iOS、Android 三份证据 |
| “能生成”代替“够好看” | 先通过一名球员 + 一个球场角落的最终材质金图，再扩角色和地图 |
| 旗舰未过审就扩 93 地图 | M1 只做一个贵州山地村场；全国内容到 M3 才开始 |
| 程序方块成为最终资产 | 程序化几何仅可做灰盒；最终近景必须来自已验收 Blender 资产 |
| 多引擎长期共存 | M0 后只保留一个正式引擎；其他实验归档且不得继续加功能 |
| 版本和 API 混用 | 锁文件、引擎版本、导出器版本、骨骼版本同时冻结 |
| 截图很多但没有阈值 | 自动检测黑帧、加载错误、视觉差异、Draw Call、纹理内存和包体 |
| 并行产生重复实现 | 同一文件单一负责人；契约和金图通过后才允许最多三路并行 |
| AI 输出直接入库 | AI 资产先进入 `quarantine`，通过许可、拓扑、LOD、文化四道检查后晋级 |
| 远程数据掩盖本地不完整 | 主包永远带通用球场；任何 CDN 失败都能完成一局 |

## 6. 模型如何正确参与

Claude 5、Codex 或后续更强模型最适合承担：

- 读取真实工程与日志；
- 编写可测试的比赛规则和工具；
- 操作 LayaAir/Galacean/Blender 的确定性接口；
- 运行统一验收并根据证据修复；
- 批量生成已被模板约束的数据配置；
- 对资产清单、包体、引用和许可证做机械检查。

它们不应独立决定：

- 最终角色是否好看；
- 某省文化是否准确；
- 真实人物肖像是否可用；
- 哪张网页截图等于真机体验；
- 尚未测试的引擎已经“适合生产”。

最终品质需要语言模型、3D 生成模型、Blender 资产规范、固定视觉靶标、真实设备和人工文化审核共同形成闭环。

## 7. 本复盘的停止结论

《乡村足球赛》不继承《人人躲猫猫》的代码，也不继续其任一引擎迁移。只继承经过验证的方法与失败约束。下一步不是再做全国地图，也不是先做完整比赛，而是完成 M0 双引擎微信真机闸门；M0 有唯一通过者后，才进入一个球场、一套球员、一整局的 M1 纵向切片。
