# 《乡村足球赛》3D 开发实施文档

> 文档版本：1.0
> 日期：2026-08-02
> 当前阶段：设计交付完成；下一开发里程碑为 M0 双引擎闸门

## 1. 开发策略

先验证微信，再做一局精品，再扩全国内容。开发顺序固定为：

```text
D0 文档与视觉方向
  → M0 LayaAir/Galacean 同题竞测
  → 锁定唯一引擎
  → M1-A 金模、动作试镜与手感实验室
  → M1-B 贵州山地主场 5v5 完整一局
  → M2 地区身份、赛季与本地排行
  → M3 九地域/34省叠加层
  → M4 真实在线排行与好友
  → M5 真机优化、提审、发布与复盘
```

一个里程碑只允许一个可验证目标。达到完成条件后更新 `STATUS.md` 并停止，不自行开始下一个里程碑。

## 2. 环境基线

当前本机已确认：

- Cocos Creator 3.8.8；
- Blender 5.1.2；
- Godot；
- 现有微信小游戏工程与开发者工具配置；
- LayaAir 尚未安装；
- Galacean 可通过 npm/CLI 建立纯代码项目。

M0-A 开始时安装 LayaAir 3.3.11 稳定版。LayaAir IDE 首次登录、MCP 插件订阅或 API Key 属于开发加速器外部状态；若用户不启用 MCP，仍须能通过命令行和普通 TypeScript 完成 M0。MCP 不得进入 CI 必需步骤。

## 4. 代码规则

### 4.1 TypeScript

- 开启 `strict`、`noUncheckedIndexedAccess` 和未使用变量检查；
- `MatchCore` 不使用 DOM、微信全局、引擎类型、日期墙钟或隐式随机；
- 所有外部输入先解析到显式 schema，再进入核心；
- 状态结构尽量使用数字、枚举和定长集合，避免模拟热路径创建临时对象；
- 渲染帧可以使用对象池，但不能复用后仍被其他系统持有的对象；
- 错误分为可恢复内容错误、平台错误、规则不变量错误和开发配置错误；
- 不吞异常；玩家看到普通语言，证据日志保留稳定错误码和上下文。

### 4.2 依赖

- 每个运行依赖必须记录版本、许可证、用途、主包影响和替代方案；
- M0 禁止引入完整物理 WASM、状态管理大框架、UI 大框架和远程脚本；
- 引擎模块按白名单启用，未使用的粒子、XR、编辑器和物理模块不进入构建；
- 锁文件和引擎版本一同提交；不使用浮动 `latest`；
- 同类外部服务失败最多重试两次，随后走本地回退或明确失败。

### 4.3 引擎端口

每个适配器只负责：

- 初始化画布和渲染器；
- 加载清单化资产；
- 创建/释放场景和角色；
- 应用表现帧；
- 动画、材质、LOD、实例化、相机和特效；
- 输出性能与截图探针。

引擎端不得实现比分、控球归属、体力、AI 决策或排行榜规则。

## 5. M0 实施

### 5.1 统一试题仓

先完成引擎无关部分：

1. `match-core`：10 名球员移动、球体滚动、短传、射门、抢断的 30 Hz 最小模拟；
2. `presentation`：从模拟状态生成球员姿态、动画意图、球、相机兴趣点和 HUD 值；
3. `assets-built/m0`：同一球场、同一角色骨架/动作、同一观众和三档配置；
4. `platform-test-contract`：触控、多点、前后台、文件缓存、分包和错误注入；
5. `evidence schema`：包体、帧时间、内存、截图和设备信息。

这部分只写一次，两个候选都消费它。

### 5.2 M0-A：LayaAir

最多两个开发工作日：

1. 固定 LayaAir 3.3.11 和对应 IDE/引擎库；
2. 建立空 3D 项目、命令行 Web/微信构建脚本；
3. 只启用 M0 需要的 3D、动画、输入和资源模块；
4. 导入统一 GLB、动作和压缩纹理；
5. 实现 `RenderPort` 最小方法；
6. 配置本地分包、远程包模拟和通用球场回退；
7. 输出微信开发者工具与可安装真机产物；
8. 记录所有 IDE 手工状态，并将其转成版本化配置或构建脚本。

若使用 LayaAir-MCP，额外记录：调用的工具、生成/修改文件、能否在关闭 MCP 后干净构建。MCP 服务不可用不能算引擎失败，只有普通构建失败才算。

### 5.3 M0-B：Galacean

最多两个开发工作日：

1. 固定 `@galacean/engine@1.6.13` 与平台适配 CLI；
2. 从 TypeScript 入口建立 Web/微信双构建；
3. 只引入 M0 需要的引擎模块；
4. 加载与 LayaAir 完全相同的 GLB、动作和纹理源；
5. 实现相同 `RenderPort` 方法；
6. 配置本地分包、远程资源模拟和通用球场回退；
7. 输出开发者工具与真机产物；
8. 记录 tree-shaking、WebGL1/2、动画和缓存行为。

### 5.4 第五日决策

- 两个候选运行同一自动输入和 10 分钟场景；
- 包体报告使用真实微信上传目录；
- iOS/Android 采用同一画质和测试路径；
- 硬门失败者直接淘汰；
- 都通过时按 `RESEARCH_3D_STACK.md` 权重评分；
- 写 `ADR-0001-3d-runtime.md`，包含原始证据路径；
- 默认构建只保留胜者；
- 更新 `STATUS.md` 并停止。

## 6. M1 实施切片

M1 拆成两个独立 Goal：M1-A 先证明金模和足球手感，M1-B 再完成贵州西南山地灵感主场、两队基础球衣、10 名角色和一整局快速比赛。

开发顺序：

1. **M1-A 金模与金角**：一名最终球员 + 25×25 米手感场先过视觉和真机门；
2. **M1-A 动作试镜**：开放样本、商业候选预览/试用和专项自捕按 FOOTBALL_FEEL.md 同题评分；
3. **M1-A 手感门**：完成三套预设、六个练习、机器指标和 5 人盲测；
4. **M1-B 规则闭环**：开球、移动、传球、射门、抢断、进球、出界、计时、结算；
5. **M1-B AI 闭环**：队形、接应、回防、门将和三档难度；
6. **M1-B 表现闭环**：动画、相机、HUD、音效、轻特效和赛果；
7. **M1-B 内容闭环**：地区/队名/球衣 → 赛前 → 主场 → 赛后本机记录；
8. **M1-B 恢复闭环**：断网、地域包损坏、低内存、后台恢复和安全模式；
9. **M1-B 真机优化**：中档 30 FPS、主包/本地包预算、热机 10 分钟；
10. **M1-B 用户盲测**：地域识别、操作完成和“不是占位画面”的定性验证。

在 M1-A 未过审前，不生产剩余角色和整场建筑；在 M1-B 完整一局未过审前，不开发赛季和全国地图。

## 7. 目标命令

M0 建立以下统一命令；它们是开发交付要求，不代表当前已经存在：

```bash
npm run check
npm run test:unit
npm run test:replay
npm run build:web
npm run build:wechat
npm run audit:assets
npm run audit:packages
npm run test:visual
npm run report:m0
```

- `check`：格式、类型、依赖和 schema；
- `test:unit`：规则、内容和资源状态机；
- `test:replay`：固定输入的状态哈希；
- `build:*`：干净构建；
- `audit:assets`：网格、骨骼、纹理、许可和文化状态；
- `audit:packages`：主包、分包、远程资源和重复文件；
- `test:visual`：固定机位、黑帧和金图差异；
- `report:m0`：合并引擎、微信和真机证据。

所有脚本非交互运行，失败返回非零状态；不依赖个人桌面路径或未登记环境变量。

## 8. 测试体系

### 8.1 单元测试

- 传球目标、射门散布、抢断角度、体力和冷却；
- 球门、边线、门柱、球网阻尼和快速重开；
- AI 感知、候选评分、队形和难度参数；
- 地区路径、球队名称、球衣冲突和默认回退；
- 资源清单、哈希、依赖、缓存、重试和版本迁移；
- 存档 schema、失败恢复和待同步队列。

### 8.2 重放测试

- 固定种子 + 固定输入在同版本产生相同状态摘要；
- 30/45/60 渲染频率不改变最终比分和核心状态；
- 暂停、前后台和卡顿追帧不改变 tick 顺序；
- 引擎 A/B 的表现不同不能改变核心哈希；
- 未来客户端与服务端用同一重放夹具检查漂移。

### 8.3 视觉测试

- 10 张固定金图；
- 黑帧/纯色帧检测；
- 缺贴图、粉色材质、NaN 变换和相机穿模检测；
- 主客队色弱模拟和文字安全区；
- LOD 跳变、脚滑和动画触球帧视频；
- 高中低三档同机位比较。

### 8.4 平台与真机

- 微信开发者工具仅证明兼容与日志，不作为性能最终结论；
- 至少一台 iOS、一台 Android 中档参考机；
- 首次启动、缓存启动、资源损坏、弱网、断网、切后台、来电/音频中断；
- 10 分钟热机帧时间、内存、发热和电量趋势；
- 触控多点、刘海安全区、不同宽高比和系统字体。

### 8.5 包体

- 真实上传目录总字节；
- 主包、每个分包、远程包分别统计；
- JS、WASM、GLB、纹理、音频、数据分类；
- 重复哈希和未引用资产；
- 高分辨率源图、参考图片、许可证不允许分发文件的误入检查。

## 9. AI 协作规则

更强模型可以加快工程，但必须受以下规则约束：

1. 每次任务只服务当前里程碑完成条件；
2. 不因发现新引擎、新模型或新玩法自行扩范围；
3. 修改前先读取当前状态、契约、金图和失败证据；
4. 同一文件同一时间只有一个修改者；
5. 最多三路并行，且任务真正独立、输出接口已冻结；
6. 每个视觉任务必须查看实际截图/视频，不凭代码声称好看；
7. 每个真机结论附设备证据，不凭模拟器声称通过；
8. AI 生成资产先进入 `quarantine`；
9. 失败最多按同一路线修复两次，第三次回到架构/范围决策；
10. 模型名、角色名或提交尾注不是质量证据。

## 10. Git 与变更管理

- 新开发使用 `codex/` 前缀功能分支或里程碑分支；
- 现有 2D 代码在 M0/M1 只读，除非迁移接口有独立批准；
- 不提交 `node_modules`、引擎缓存、Unity/Laya Library、原始 AI 高模、临时截图和生产凭据；
- 小型源资源与运行资产都必须能追溯到源登记；
- 构建产物通过报告保存哈希，是否提交由项目现有发布规范决定；
- 一个提交只包含一个可说明的产品/技术变化；
- 里程碑提交前工作树中与本任务无关的用户修改不得被暂存或覆盖。

## 11. 完成定义

一个功能只有同时满足以下条件才称为“本地实现完成”：

- 需求与异常路径实现；
- 单元/集成/重放测试通过；
- 视觉任务有金图和人工检查；
- 资产、包体和依赖检查通过；
- 目标平台证据符合该里程碑要求；
- 文档与 `STATUS.md` 更新；
- 没有以假数据冒充真实服务。

“本地实现完成”仍不等于真实服务接入、部署、提审或生产验收；这些状态必须分别记录。
