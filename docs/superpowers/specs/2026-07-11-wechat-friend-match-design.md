# 微信小游戏好友实时对战设计规格

日期：2026-07-11
目标工程：`wechat-minigame-original-runtime-latest`
状态：设计已确认，待实施

## 1. 目标

在不削减现有球队、双方阵型、难度和比赛时长设置的前提下，为微信小游戏增加一对一好友实时对战：邀请者控制红队，被邀请者在自己的手机上控制蓝队，双方看到同一场完整比赛。

首页默认仍是单人对 AI，新玩家进入后可以直接点击醒目的金色“立即开赛”；“好友对战”作为独立入口，通过微信分享卡片邀请一名好友作为对手。发出邀请后，房主等待好友期间仍可先和 AI 比赛，好友上线后可以观战这场热身赛，再由房主结束热身赛并开启正式好友局。

本功能的成功标准不是“分享链接可以打开”，而是两台真机在不同网络下能加入同一房间、同步开赛、完成整局，并始终保持相同的比分、时间、球和球员状态。

## 2. 已确认的产品决策

### 2.1 首页三个对称入口

- 完整保留左右球队、双方阵型、难度和比赛时长等现有选择，不折叠、不删除，也不因新手路径而简化高级玩法。
- 底部固定为三个左右对称的按钮：左侧“观看对战”、中间“立即开赛”、右侧“好友对战”。
- “立即开赛”的几何中心位于页面中轴，保持金色、较大尺寸和最高视觉权重；左右按钮同宽同高并关于中轴对称。
- “立即开赛”保持一步启动本机对 AI，不增加确认弹窗。
- 点击“好友对战”时，使用用户已经选好的双方球队、阵型、难度和时长创建房间并立即拉起微信分享。
- 好友未上线时，房主可留在等待页、再次邀请、取消等待，或者选择“先跟 AI 对战”。

### 2.2 双方身份和配置权限

- 邀请者固定为房主和红方；被邀请者固定为蓝方和对手方。
- 房主创建房间时，当前选择的双方球队、阵型、难度和时长即被冻结为正式好友局配置。
- 好友加入后不能修改球队或阵型；分享参数本身也不承载可信配置，好友从服务端取得房主冻结的配置。
- 好友上线即表示可以开始，无需再经过一层球队配置或准备按钮；房主决定何时结束等待或 AI 热身并开启正式好友局。
- 球队中未被真人直接控制的球员继续由现有 AI 控制；难度设置因此继续保留。

### 2.3 等待和开赛流程

房主流程：

1. 在首页点击右侧“好友对战”。
2. 客户端创建两人房间，获得不可猜测的邀请令牌。
3. 拉起微信分享卡片；取消分享不会销毁房间，等待层提供“再次邀请”。
4. 等待好友期间，房主可选择“先跟 AI 对战”；这场比赛是热身赛，房间和邀请继续有效。
5. 好友上线后，若房主正在热身，暂停比赛并弹出两个选择：“立即好友对战”和“踢完这局”。
6. 选择“立即好友对战”会结束 AI 热身并立刻准备正式比赛；选择“踢完这局”会恢复热身并记录排队状态，AI 全场结束后自动切入正式好友局，不再弹出第二次确认。
7. 房主进入好友对战后，正式比赛从 0:0 重新开始，不继承热身赛比分和比赛时间。
8. 双端完成比赛资源加载后，服务端下发统一开球时间，显示 3、2、1 倒计时并进入比赛。

好友流程：

1. 打开分享卡片，读取 `invite` 和协议版本参数。
2. 显示“好友邀请你对战”预览以及双方球队、阵型和时长。
3. 点击“加入对战”，加入后固定为蓝方并通知房主自己已上线。
4. 房主未开赛时停留在等待页；若房主正在跟 AI 热身，好友可以继续等待，也可以点击“观看热身赛”进入只读观战。
5. 房主选择“踢完这局”后，好友端显示“房主踢完本局后与你对战”；房主正式开赛时，无论好友正在等待还是观战，都自动加载正式比赛并进入蓝方操控。

如果用户正在进行一场单机比赛时收到热启动邀请，先暂停当前比赛并询问是否退出当前比赛加入好友局，不能直接销毁正在进行的比赛。

## 3. 实现路线比较与结论

### 方案 A：房主设备权威模拟（采用）

房主设备以现有 60 Hz 比赛循环运行完整物理和 AI。好友设备只上传蓝方操作；房主把它写入引擎已有的第二玩家输入通道，并以 20 Hz 下发权威比赛帧。好友设备缓冲并插值这些帧，只负责渲染，不独立推进物理。

优点是可复用现有 `__touchInput2`、第二控制器和 `MatchStream`，服务端无需运行浏览器/Pixi 比赛内核，并且不会因为随机数或设备时间步差异导致两端比赛分叉。缺点是好友操作需要经过房主，网络延迟高时蓝方手感会比红方稍慢；首版通过同区域部署、30 Hz 输入上报和 120 ms 插值缓冲控制延迟。

### 方案 B：双端确定性锁步（不采用）

两台手机各自模拟比赛，仅交换输入。它的带宽低，但当前内核从系统时间或加密随机源生成种子，比赛过程还使用多套随机数；缺少全局确定性、状态校验、回滚和恢复。直接使用会出现比分或球员位置逐渐不同的“假同步”，风险不可接受。

### 方案 C：服务器权威模拟（暂不采用）

把完整比赛内核运行在服务器，两端都只上传输入和渲染状态。公平性与主机退后台恢复最好，但当前内核依赖浏览器和 Pixi，迁移成无渲染服务器模拟的工程量远超首版好友对战。

## 4. 系统架构

```text
房主（红方）
本机触控 ───────────────→ 原版控制器 1
好友输入 → __touchInput2 → 原版控制器 2 → 60 Hz 权威比赛模拟
                                           │
                                           └─ 20 Hz 权威帧
                                                   │
微信 WSS 房间服务 ← 房间/加载/心跳/重连 ───────────┤
       │                                           │
       └─ 转发好友输入 ─→ 房主                    ↓
                                            好友（蓝方）
好友本机触控 ─ 30 Hz 输入上报             120 ms 帧缓冲 + 插值渲染
```

系统分成四个边界清晰的单元：

1. **好友房间界面**：负责分享、等待、AI 热身入口、好友上线提示、热身观战、错误和重连提示，不处理网络协议细节。
2. **房间客户端**：负责身份、WebSocket、协议消息、心跳、重连和房间状态，把稳定事件暴露给应用层。
3. **比赛同步适配层**：房主注入蓝方远端输入并导出权威帧；好友关闭本地物理推进，只把收到的帧写入渲染流。
4. **房间服务**：只维护两人房间、冻结配置、等待/热身/正式比赛状态和消息中继，不计算比赛物理。

## 5. 客户端改造

### 5.1 应用和启动参数

`src/app/main.js` 负责好友局顶层生命周期：

- 冷启动通过 `wx.getLaunchOptionsSync()` 读取邀请参数；
- 热启动通过 `wx.onShow()` 的进入参数读取邀请参数；
- 使用邀请令牌去重，避免冷启动和 `onShow` 重复加入同一房间；
- 分享 query 只携带 `invite=<opaque-token>&v=1`，球队、阵型和身份均从服务端读取；
- 分享 API 没有可靠的“好友已完成转发”结果，因此取消分享只返回等待房，不发奖励、不自动开赛；
- 正在单机比赛时收到邀请，先暂停并显示退出确认。

`src/data/game-options.js` 增加好友房、热身和观战所需的内部模式并保留 `roomId`，但任何来自分享 query 的比赛配置都不可信。

### 5.2 房间界面

`src/ui/game-shell.js` 保留当前所有设置，在“立即开赛”右侧增加与左侧按钮对称的“好友对战”。新增独立的房间层，至少覆盖以下状态：

- 创建房间中；
- 等待好友，可再次邀请、取消等待或先跟 AI 对战；
- 房主正在 AI 热身，好友尚未上线；
- 好友已上线，房主可继续热身或开始好友对战；
- 房主已选择踢完热身后自动开始，好友端显示排队状态；
- 好友等待房主，并可在房主热身时进入观战；
- 好友正在只读观战房主热身赛；
- 加载比赛和同步倒计时；
- 房间已满、邀请过期、版本不兼容、连接失败或房主离开。

房间层使用现有 Canvas/Pixi UI 体系，不引入 DOM 或 React。

### 5.3 房间客户端

在正式工程新增 `src/net/room-client.js`，不直接复用旧原型中“双方各自模拟、只交换输入”的实现。对外只暴露：

- `connect()` / `close()`；
- `createRoom()` / `joinInvite()`；
- `startWarmup()` / `endWarmup()` / `requestStart()`；
- `sendInput()` / `sendSnapshot()`；
- 房间状态、加载、开球、暂停、恢复、比赛结束和错误事件。

WebSocket 自动心跳并采用有上限的指数退避重连。恢复时使用服务端签发的短期恢复令牌重新绑定原房间和原队伍，客户端不能自行声明 host、红方或蓝方。

### 5.4 比赛同步适配

现有原版内核已经具备第二玩家通道：`__touchInput2`、第二控制器、蓝队绑定和自动切人。本功能只把远端蓝方输入接入这条路径。

- 房主热身模式：继续按普通本机 AI 对战运行，同时以 20 Hz 发布热身赛权威帧；好友上线不自动中断，先暂停并让房主选择继续或开始好友局。
- 房主选择“踢完这局”后设置一次性排队标记；监听 `ab-match-ended`，热身结束即清除标记并发起正式开赛，不再显示第二次确认。
- 好友热身观战模式：不发送控制输入，也不运行本地物理，只接收房主热身帧并插值渲染。
- 正式好友房主模式：继续以 60 Hz 推进完整比赛；本机输入驱动红方，最新的远端输入驱动蓝方；每个输入消息带 `matchId`、单调递增 `seq` 和客户端采样帧号，重复或倒序消息被丢弃。
- 正式好友蓝方模式：禁止调用本地 `pitch.update` 推进物理；接收房主帧后写入初始值为 120 ms 的帧缓冲，使用现有插值能力渲染，同时以 30 Hz 上传蓝方输入。
- 房主以 20 Hz 发送二进制权威帧；比分、比赛时间、球、双方球队和球员、镜头及关键事件均来自同一帧。
- 好友以 30 Hz 发送连续输入；传球、射门等脉冲动作带序号，确保一次按下只消费一次。
- 切入后台、断线或离开比赛时立即清空连续输入，避免球员持续奔跑或蓄力。

生成的运行时代码不手工修改；第二玩家、快照导出和好友只渲染分支由 `tools/build.mjs` 的构建补丁生成，`src/boot/start.js` 只负责选择角色和连接适配层。

## 6. 房间服务与协议

首版服务采用 Node.js 单实例 WSS，中继服务不保存长期个人资料。等待房间创建后 10 分钟未开赛即过期；比赛房间在正常结束后立即回收，并设置 30 分钟硬过期上限。

### 6.1 身份和权限

- 客户端通过 `wx.login` 获得一次性 code，经 WSS 交给服务端调用微信 `code2Session`；AppSecret 只保存在服务端。
- 服务端签发短期会话和恢复令牌；邀请令牌、会话令牌和恢复令牌用途分离。
- 邀请令牌必须高熵、不可枚举、可过期，只用于加入指定房间，不能直接代表玩家身份。
- 服务端固定分配房主/红方和好友/蓝方；每房最多两人，第三人收到“房间已满”。
- 房间配置在创建时冻结，好友不能修改；只有房主能开始/结束热身并请求正式开赛。

### 6.2 协议消息

控制消息使用带协议版本的 JSON；高频比赛快照使用带固定头部的二进制消息。首版消息集合：

- 客户端到服务端：`auth`、`create_room`、`join_invite`、`warmup_start`、`warmup_end`、`spectate_start`、`load_ready`、`start_request`、`input`、`snapshot`、`ping`、`resume`、`leave`、`match_end`；
- 服务端到客户端：`auth_ok`、`room_created`、`room_state`、`load_match`、`kickoff_at`、`input`、`snapshot`、`pause`、`resume_ok`、`match_end`、`pong`、`error`。

所有消息都包含协议版本；比赛期消息包含 `roomId`、`matchId` 和递增序号。服务端校验消息类型、角色权限、字段范围、载荷大小和发送频率，不能信任客户端自报 slot 或 role。

### 6.3 开球握手

房主请求开赛后，服务端冻结房间配置并生成新的 `matchId`，向双方发送 `load_match`。双方加载完成并回复 `load_ready` 后，服务端根据其时钟下发至少 3 秒后的 `kickoff_at`。房主从该时刻开始权威模拟，好友以收到的权威帧为准；任何一方加载失败都会取消开球并回到可恢复的等待状态。

## 7. 断线和异常处理

- 短暂丢包或 0–3 秒连接中断：比赛顶部显示弱提示，立即清空断线一方输入。
- 中断超过 3 秒：权威房主暂停比赛，双方进入重连层，房间保留 20 秒。
- 20 秒内恢复：服务端恢复原身份和队伍，下发最新完整帧，双方显示 3 秒倒计时后继续。
- 蓝方超过 20 秒未恢复：房主可选择“AI 接管”或“结束本局”；不自动替好友做决定。
- 房主超过 20 秒未恢复：由于权威模拟在房主设备上，首版直接结束好友局并说明原因，不做主机迁移。
- 赛前好友离开：回到“等待好友”，不能悄悄改为 AI 并自动开赛。
- 房间已满、邀请过期、协议版本不兼容、鉴权失败和服务不可用都必须给出明确中文提示，以及重试、返回首页或改玩 AI 的可执行出口。

## 8. 安全、合规和部署要求

- 正式服务必须使用有效 TLS 证书的 `wss://` 域名；如登录另走 HTTPS，还需独立配置请求域名。
- 在微信公众平台“开发设置”的服务器域名中配置 Socket 合法域名；真机不会接受仅在开发者工具中关闭域名校验的配置。
- 域名备案、证书链和 TLS 版本必须满足微信当前上线要求。
- 服务端设置连接数、房间数、单连接发送频率和二进制载荷上限，拒绝未知字段和越权消息。
- 首版单实例部署，不宣称无缝多机扩容；需要多实例时再引入 Redis 房间状态和跨实例发布订阅。
- 首版不采集头像、昵称、手机号或通讯录；如果后续增加这些资料，必须同步更新隐私指引和数据处理说明。

## 9. 测试方案

### 9.1 单元与协议测试

- 首页三个按钮左右对称、中间“立即开赛”居中且默认 AI 行为正确；
- 分享参数生成、冷/热启动读取和邀请去重正确；
- 房间配置由房主创建时冻结、好友不能篡改且只有房主能结束热身并正式开赛；
- 第三人、过期令牌、伪造角色、越权配置和重复序号被拒绝；
- 输入脉冲只消费一次，连续输入在断线和切后台时清零；
- WebSocket 心跳、重连退避、恢复令牌和房间过期；
- 权威帧二进制编码、解码和插值前后关键状态一致；
- 好友只渲染模式不会偷偷运行本地物理。

### 9.2 集成和故障测试

- 两个客户端通过本地 WSS 创建、分享参数加入、完成加载并同步开赛；
- 房主等待时启动 AI 热身，好友上线后能收到热身快照并进入只读观战；
- 房主从热身切换到正式好友局时双方重新加载且比分、时间从零开始；
- 模拟 50、100、200 ms 延迟及轻度抖动，双方比分和最终赛果始终一致；
- 模拟乱序/重复输入、短断网、20 秒内恢复和恢复超时；
- 房主或好友切后台时比赛暂停，返回后身份和队伍不交换；
- 比赛结束后双方结果页一致，房间被回收。

### 9.3 微信真机验收

- iPhone 与 Android 各至少一台，分别使用 Wi-Fi 和移动网络完成整局；
- 从微信会话分享卡片冷启动和小游戏热启动都能正确加入；
- 双方开球、比分、计时、进球事件和最终结果一致；
- 蓝方能移动、自动切人、传球、挑传、铲球、射门和冲刺；
- 断线恢复、房满、邀请过期和版本不兼容提示可理解且可退出；
- 一整局无明显输入粘连、状态跳回、持续积累的内存增长或崩溃。

## 10. 实施顺序和上线闸门

实现按一个可验证的纵向切片推进：

1. 首页三按钮、等待房和邀请参数；
2. 房间服务、身份、冻结配置、AI 热身状态和开球握手；
3. 蓝方远端输入接入现有第二玩家通道；
4. 权威帧导出、好友只渲染和插值；
5. 暂停、心跳、重连和结束流程；
6. 本地双客户端、微信开发者工具和双真机验收；
7. 部署正式 WSS 并配置微信合法域名后才开放入口。

在热身观战、权威帧同步、双真机整局一致性、断线恢复和正式 WSS 配置全部通过前，不得把“好友对战”作为正式可用功能发布。开发阶段可用显式测试开关展示入口。

## 11. 明确不做

- 不删除或简化多球队、多阵容等高级设置；
- 不做陌生人匹配、排行榜、第三人观战或多人房间；好友只可观战邀请者等待期间的 AI 热身赛；
- 不做主机迁移、服务器权威物理或回滚预测；
- 不为好友私房赛增加排行榜、奖励或正式反作弊；如后续加入竞技结果，必须改用更强的服务器权威方案；
- 不把分享完成当作可靠事件，也不据此奖励用户；
- 不使用双方各自模拟、仅交换输入的旧原型冒充实时同步；
- 不在首版采集头像昵称，不增加好友关系或聊天系统；
- 不在本功能中接入广告或支付。
